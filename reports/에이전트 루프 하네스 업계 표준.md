# 루프는 모델이 돌리고, 종료는 하네스가 결정한다

> 조사 기준일: 2026-11-18. 표기 규칙: **[2차]**는 1차 원문을 직접 확인하지 못하고 요약·보도·개인 블로그에 의존한 주장, **[개인]**은 실무자 개인 의견, **[폐기]**/**[대체]**는 공식적으로 deprecated되었거나 다른 것으로 대체된 항목이다. 마지막 장 "loop-harness를 위한 권고"는 조사 결과가 아니라 그에 근거한 필자의 제안이다.

Anthropic, OpenAI, Google이 공개한 에이전트 설계 원칙은 서로 다른 어휘를 쓰지만 같은 구조를 가리킨다. 모델이 "맥락 수집 → 행동 → 검증"을 반복하는 단순한 루프를 돌리고, 그 바깥의 **하네스**가 무엇을 볼지(컨텍스트), 무엇을 만질지(샌드박스·권한), 언제 끝낼지(결정적 검증 게이트와 반복·예산 상한)를 강제한다. 세 회사 모두 "가장 단순한 단일 에이전트 루프로 시작하고, 복잡성은 효과가 입증될 때만 더하라"고 말한다. 장기 실행 상태는 컨텍스트 창이 아니라 git, 진행 파일, append-only 이벤트 로그 같은 외부 저장소에 둔다. 완료 판정은 모델의 자기 보고가 아니라 테스트·린트·빌드의 exit code로 내린다. 표준 측면에서는 2025-12-09 Linux Foundation 산하에 출범한 Agentic AI Foundation(AAIF)이 **AGENTS.md(프로젝트 지시)**와 **MCP(도구 연결)**를 관리하고, 2026-08에는 **A2A(에이전트 간 통신)**도 합류했다. **Agent Skills(SKILL.md)**는 agentskills.io의 오픈 스펙으로 Codex, Gemini CLI, Copilot, Claude Code가 모두 읽는다. 반면 **hooks**에는 공식 표준이 없고, Claude Code의 이벤트 모델(stdin JSON, exit 2 = 차단)이 사실상의 표준 역할을 한다. 국내에서는 카카오페이, 토스, 우아한형제들, 컬리, LY/LINE이 같은 결론을 공개했다. "실수는 프롬프트가 아니라 구조로 막는다"는 것, 그리고 모델이 좋아지면 하네스를 줄여야 한다는 것이다. 도구 비종속 루프 엔지니어링 환경을 만들려면 이 공통분모(AGENTS.md + `.agents/skills` + MCP + Claude식 hook 계약 + exit-code 게이트 + 이벤트 로그)를 기본값으로 삼으면 된다.

## 세 회사의 루프는 "gather → act → verify + 명시적 종료 조건"으로 수렴했다

Anthropic의 기초 문헌은 2024-12-19에 나온 "Building effective agents"다. 이 글은 에이전트를 **"환경 피드백(ground truth)을 받으며 루프 안에서 도구를 쓰는 LLM"**으로 정의한다. 미리 정한 코드 경로로 흐르는 *workflow*와 모델이 흐름을 정하는 *agent*를 구분하고, prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer의 다섯 패턴을 제시한다. 종료 조건으로는 최대 반복 횟수 같은 stopping condition을 두고, 막히면 사람에게 넘기라고 권한다 ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). 이 정의는 이후 Claude Agent SDK에서 **"gather context → take action → verify work → repeat"**라는 루프 공식으로 굳어졌다 ([Agent SDK blog](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)). 현재 Claude Code 문서는 하네스를 명시적으로 이렇게 정의한다. "모델 주위에서 도구를 제공하고 모델이 보는 컨텍스트를 관리하는 층" ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)).

OpenAI의 Agents SDK Runner도 같은 구조다. LLM을 호출해 최종 출력이 나오면 종료하고, handoff면 에이전트를 교체하고, 도구 호출이면 실행 후 반복한다. 이 전체를 **`max_turns`**로 묶고, 초과하면 `MaxTurnsExceeded` 예외를 던진다. 가드레일은 입력, 출력, 도구 세 단계에서 tripwire 예외로 실행을 끊는다. 사람의 승인이 필요하면 `RunState`를 직렬화해 멈췄다가 재개한다 ([Agents SDK: Running agents](https://openai.github.io/openai-agents-python/running_agents/); [Guardrails](https://openai.github.io/openai-agents-python/guardrails/)). OpenAI의 "A practical guide to building agents"(2025-04 무렵 PDF)도 요약본 기준으로는 같은 노선이다. 단일 에이전트, 도구, 명시적 종료 조건(최종 출력 도구, 도구 호출 없는 응답, 에러, max turns)으로 시작하고, 멀티에이전트(manager/decentralized)는 병목이 생길 때만 도입한다. 실패 임계치를 넘거나 고위험 행동이면 사람이 개입한다 **[2차]** ([Aktagon 요약](https://cheat.aktagon.com/sheets/agents/); [ibl.ai 요약](https://ibl.ai/blog/openai-a-practical-guide-to-building-agents.md)). Codex의 루프를 해부한 "Unrolling the Codex agent loop"(2026-01-23)는 원문이 403으로 막혀 요약으로만 확인했다 **[2차]**. 내용은 이렇다. 한 사용자 turn 안에서 도구 호출이 수백 번 일어날 수 있으므로 컨텍스트 관리는 하네스의 책임이다. 프롬프트 캐시를 지키려고 대화를 append만 하고, 압축이 필요하면 `/responses/compact`를 쓴다 ([InfoQ](https://www.infoq.com/news/2026/02/codex-agent-loop)).

Google은 "모델 + 도구 + 오케스트레이션 레이어"라는 틀을 쓰고, 오케스트레이션 레이어가 think-act-observe 루프를 돌린다. 2025-11 Kaggle 5일 과정의 5부작 백서(Introduction to Agents → Tools/MCP → Context Engineering → Agent Quality → Prototype to Production)가 현재 기준 레퍼런스다. 백서 원문은 추출하지 못해 요약으로만 확인했다 **[2차]** ([Analytics Vidhya](https://www.analyticsvidhya.com/blog/2025/11/ai-agent-research-papers-by-google/); [ppc.land](https://ppc.land/google-cloud-releases-comprehensive-agentic-ai-framework-guideline/)). ADK 문서는 이 루프를 가장 결정론적으로 기술한다. `LoopAgent`는 종료를 스스로 결정하지 않으므로 **`max_iterations` 또는 `escalate`(`exit_loop` 도구) 중 하나가 반드시 있어야 한다**. 대표 예시는 writer → (critic → refiner, max 5회) 구조다 ([ADK Loop agents](https://adk.dev/agents/workflow-agents/loop-agents/)). 다만 같은 페이지에 Loop/Sequential/Parallel "template workflows"를 graph/dynamic workflows로 대체하라는 공지가 붙어 있다 **[대체]**.

| 관점 | Anthropic | OpenAI | Google |
|---|---|---|---|
| 루프 정의 | gather → act → verify → repeat | LLM → (final / handoff / tool) 반복 | think → act → observe |
| 종료 강제 | Stop hook, `--max-turns`, `--max-budget-usd` | `max_turns`, guardrail tripwire | `max_iterations`, `escalate`/`exit_loop` |
| 기본 권고 | 가장 단순한 해법부터 | 단일 에이전트부터 | 결정론적 컨트롤러가 반복 통제 |
| 검증자 분리 | evaluator-optimizer, fresh reviewer | `/review` 별도 리뷰어, trace grading | critic → refiner, trajectory eval |

세 회사가 공유하는 설계 입장은 분명하다. **반복 여부와 종료는 코드(하네스)가 소유하고, 모델은 루프 안의 한 스텝을 판단한다.** HumanLayer의 12-Factor Agents도 이것을 "Own your control flow"로 정식화했다 **[개인]** ([humanlayer.dev](https://humanlayer.dev/blog/12-factor-agents)). Stripe의 Blueprints는 결정적 노드("Run configured linters")와 에이전트 노드("Fix CI failures")를 섞은 코드 정의 워크플로로 프로덕션에서 같은 원칙을 구현한다 ([Stripe Minions Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)).

## 하네스의 핵심은 모델의 자기 보고를 믿지 않는 결정적 검증 게이트다

Anthropic이 2026년 Claude Code 문서에서 가장 강조하는 단일 조언은 **"pass/fail이 나오는 체크를 줘서 Claude가 스스로 루프를 닫게 하라"**다. 근거는 "Claude stops when the work looks done"이라는 관찰이다. 체크가 없으면 사람이 테스트 스위트 노릇을 하게 된다. 문서는 하네스 기능을 두 축으로 나눈다. 모델이 따를지 판단하는 *비결정적* 장치(CLAUDE.md, 프롬프트, skill)와 하네스가 강제하는 *결정적* 장치(hook, deny 규칙, sandbox, Stop hook, `--max-turns`/`--max-budget-usd`)다. 원칙은 **"매번 일어나야 하는 일은 hook, deny 규칙, managed setting으로 만들고, CLAUDE.md는 가이드라인용"**이다. Stop hook은 턴이 끝날 때 스크립트를 실행하고, exit 2를 받으면 stderr를 이유로 작업을 재개시킨다. 도구 호출 없이 8번 연속 차단되면 무한 루프를 막기 위해 override된다 ([Best practices](https://code.claude.com/docs/en/best-practices)). Codex도 같은 기능을 공식 제공한다. `Stop` 이벤트에서 `decision:"block"`을 반환하면 reason이 새 프롬프트가 되어 루프가 이어진다 ([Codex docs: Hooks](https://learn.chatgpt.com/docs/hooks)). Huntley의 Ralph loop가 셸 `while` 문으로 하던 "완료 조건을 만족할 때까지 반복"이 이제 두 주요 CLI에 하네스 기능으로 들어간 셈이다.

자기평가를 믿지 않는 이유는 실험 결과에 있다. Anthropic Labs의 "Harness design for long-running application development"(2026-03-24)는 **"agents reliably skew positive when grading their own work"**라고 보고하고, 생성자와 분리된 evaluator가 Playwright로 실제 UI·API·DB를 검사하게 했다. 각 sprint 전에는 generator와 evaluator가 "무엇을 만들고 어떻게 검증할지"를 **sprint contract**로 합의한다. 비용 차이는 크다. 레트로 게임 메이커 과제에서 solo 실행은 20분·$9였지만 핵심 기능이 깨져 있었고, full harness는 6시간·$200이 들었다 ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). Anthropic은 LLM-as-judge를 "견고하지 않고 지연과 비용이 늘어나므로 이득이 그만한 가치가 있을 때만" 쓰라고 하고, 규칙 기반 피드백(lint, 타입)을 1순위로 둔다 ([Agent SDK blog](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)). Thoughtworks의 Birgitta Böckeler는 이를 2×2로 정리했다. 행동 전에 조향하는 **guides(feedforward)**와 행동 후에 관찰하는 **sensors(feedback)**, 그리고 결정적이고 빠른 **computational** 검사와 의미 판단을 하는 **inferential** 검사다. 시점은 "keep quality left"로 나눈다. 커밋 전에는 빠른 lint와 test, 통합 후에는 mutation과 아키텍처 리뷰, 상시로는 drift sensor를 돌린다 **[개인]** ([martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)).

대규모 실무 사례도 같은 결론이다. Google의 사내 코드 마이그레이션 경험 보고서(arXiv:2501.06972)는 Code Search/Kythe/AST로 결정론적 탐색을 하고, LLM이 후보를 병렬 생성하고, 빌드와 테스트로 검증하고, 실패하면 에러를 넣어 수리하고, 최선의 후보를 고른 뒤 사람 리뷰와 점진 롤아웃으로 마무리하는 루프를 제시한다. JUnit3→4 전환에서는 5,359개 파일에서 **AI 생성 코드의 약 87%가 수정 없이 커밋**됐고, 병목은 리뷰어 용량이었다. 성공 지표는 AI 코드 비율이 아니라 end-to-end 소요시간이다 ([arXiv](https://arxiv.org/html/2501.06972v1)). Stripe Minions는 주당 1,300개 이상의 PR을 머지하는데, CI를 **최대 2라운드**로 제한한다. 1차 CI 후 autofix를 하고, 에이전트가 한 번 더 고치고, 2차 CI 뒤에는 사람에게 넘긴다 ([Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)). OpenAI의 "Harness engineering"(2026-02-11) 사례는 원문이 403이라 요약으로만 확인했다 **[2차]**. 요약에 따르면 엔지니어 7명이 약 5개월 동안 약 100만 줄, 1,500개 PR을 손코딩 0줄로 만들었다. 핵심은 계층 의존 방향을 커스텀 linter와 구조 테스트로 기계적으로 강제하고, **linter 에러 메시지에 수정 방법을 적어** 실패 출력이 그대로 다음 컨텍스트가 되게 한 것이다 ([businessdatasolutions 요약](https://businessdatasolutions.github.io/ai-wiki/sources/2026-02-11-lopopolo-codex-harness-engineering)).

결정적 게이트도 구현을 잘못하면 무력해진다. 이 점을 가장 구체적으로 보여 준 것은 카카오페이의 회고다. 에이전트가 lint 명령 뒤에 `| tail`을 붙이자 exit code가 tail의 것이 되어 **lint 실패가 통과로 기록**됐다. 위임 가드 hook은 출력 포맷 오류 때문에 실제 세션에서 아무 동작도 하지 않았는데 유닛테스트는 통과했다. lint 선존재 확인용 `git stash`는 공유 워킹트리에 있던 다른 세션의 미커밋 작업을 날렸다 ([카카오페이 기술블로그](https://tech.kakaopay.com/post/ai-agent-2/)). 게이트의 신뢰성 자체가 하네스가 검증해야 할 대상이라는 뜻이다.

평가 쪽에서 Anthropic은 용어를 task, trial, grader, transcript, outcome으로 표준화했다. **outcome은 에이전트의 주장이 아니라 환경의 최종 상태**다. 권고는 실패 사례 20~50개로 시작할 것, 경로가 아니라 결과를 채점할 것, pass@k(k번 중 1번 성공)와 pass^k(k번 모두 성공)를 구분할 것이다. 회당 성공률이 75%라도 3연속 성공 확률은 약 42%에 그친다 ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). ADK는 최종 응답과 함께 도구 호출 궤적(trajectory)을 채점한다 ([ADK Evaluate](https://adk.dev/evaluate/)). OpenAI는 trace grading으로 실행 과정 자체에 점수를 붙인다 ([OpenAI Trace grading](https://developers.openai.com/api/docs/guides/trace-grading)). 하네스의 기여가 얼마나 큰지는 출처마다 다르다. Terminal-Bench 2.0에서 같은 GPT-5.3-Codex가 Terminus 2에서는 64.7%, SageAgent에서는 78.4%를 기록했다는 서베이가 있다 ([arXiv 2606.20683](https://arxiv.org/pdf/2606.20683)). 반면 원 논문 쪽에서는 모델 교체가 scaffold 교체보다 효과가 크다는 반론이 나온다 **[2차]** ([emergentmind](https://www.emergentmind.com/papers/2601.11868)). 확실한 것은 **벤치마크 점수가 "모델+하네스" 조합의 점수**라는 점이다. SWE-bench Verified는 오염과 포화 때문에 SWE-bench Pro로 대체되는 중이라는 보도가 있다 **[2차, 대체 진행 중]** ([scale.com](https://scale.com/blog/swe-bench-pro); [tessl.io](https://tessl.io/blog/openai-moves-beyond-swe-bench-verified-as-coding-benchmarks-saturate/)).

## 장기 실행 상태는 컨텍스트 창이 아니라 git·진행 파일·이벤트 로그에 산다

Anthropic의 "Effective harnesses for long-running agents"(2025-11-26)는 세션 간 기억 단절을 "인수인계 노트 없는 교대근무"에 비유한다. 해법은 역할 분리다. **initializer 에이전트**가 첫 세션에서 `init.sh`, `claude-progress.txt`, 200개 이상의 기능을 모두 failing으로 둔 **feature list JSON**, 첫 git commit을 만든다. **coding 에이전트**는 이후 세션마다 한 기능만 구현하고 머지 가능한 clean state로 끝낸다. 세션 시작 루틴은 `pwd` → git log와 progress 읽기 → 최우선 미완료 기능 선택 → `init.sh`와 기본 E2E 실행 순서다. 새 작업 전에 이미 깨진 상태를 먼저 찾기 위해서다. feature list를 Markdown이 아니라 JSON으로 둔 이유는 모델이 엉뚱하게 고칠 가능성이 낮기 때문이고, 에이전트는 `passes` 필드만 바꿀 수 있다 ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). 이 방식은 Huntley의 Ralph loop("루프당 한 항목", `specs/` + `fix_plan.md`를 매번 결정적으로 로드, 매 루프 새 컨텍스트) **[개인]** ([ghuntley.com/ralph](https://ghuntley.com/ralph/))와 HumanLayer의 Research → Plan → Implement(단계마다 새 컨텍스트, 상태는 plan 파일에 압축) **[개인]** ([humanlayer.dev](https://humanlayer.dev/blog/advanced-context-engineering))와 같은 계보다.

Anthropic의 Managed Agents(2026-04-08)는 이 구조를 플랫폼 아키텍처로 일반화했다. 세 컴포넌트는 각각 따로 교체되고 따로 실패할 수 있다. **Session**은 append-only 이벤트 로그이고, **Harness**는 stateless 루프로 `wake(sessionId)` 호출 시 마지막 이벤트부터 재개한다. **Sandbox**는 `execute(name, input) → string` 인터페이스 하나만 가진 "cattle" 컨테이너다. compaction은 되돌릴 수 없으므로 원본은 모두 세션 로그에 남긴다. 자격증명은 샌드박스 밖(vault, 프록시)에 둔다. 디커플링 후 TTFT p50은 약 60% 줄었다. 이 글은 스스로를 "meta-harness"라고 부르며, 인터페이스 모양에는 의견을 갖되 그 뒤에서 Claude Code가 돌든 작업별 하네스가 돌든 상관하지 않는다고 말한다 ([Managed Agents](https://www.anthropic.com/engineering/managed-agents)). Google ADK의 컨텍스트 엔지니어링 글(2025-12-04)도 같은 분리를 제시한다. **"Context is a compiled view over a richer stateful system"**이라는 문장 아래, 저장(Session 이벤트 로그, Memory, 핸들로 참조하는 Artifacts)과 표현(매 호출마다 재구성되는 working context)을 나누고, 캐시 효율을 위해 안정적인 내용을 prefix에 둔다 ([Google Developers Blog](https://developers.googleblog.com/architecting-efficient-context-aware-multi-agent-framework-for-production/)). OpenAI 하네스 엔지니어링 글의 요약에 따르면 OpenAI는 **저장소를 단일 기록 원천**으로 삼았다. `docs/exec-plans/active|completed`, tech-debt tracker, quality score를 버전 관리했고, 슬랙이나 사람 머릿속 지식은 "에이전트가 못 보면 없는 것"으로 취급했다 **[2차]** ([businessdatasolutions](https://businessdatasolutions.github.io/ai-wiki/sources/2026-02-11-lopopolo-codex-harness-engineering)).

메모리와 지시 파일의 크기에는 모두 신중하다. Anthropic의 최신 글 "The components of agent memory"(2026-11-06)는 메모리를 transcript, 노트, 구조화 표현, 주입 컨텍스트의 4계층으로 나눈다. 주입층은 작게 유지하라고 하는데, 잘못된 노트가 모든 세션으로 퍼지기 때문이다. 또 **더 긴 지시 파일은 준수율을 낮춘다**고 하며, "메모리가 무엇을 위한 것인지는 알려 주되 어떻게 쓸지는 지시하지 말라"고 권한다 ([Agent memory](https://www.anthropic.com/engineering/components-of-agent-memory)). Claude Code는 CLAUDE.md를 200줄 미만으로 쓰라고 권한다 ([Best practices](https://code.claude.com/docs/en/best-practices)). OpenAI 사례의 AGENTS.md는 약 100줄짜리 "지도"로 `docs/`에 연결된다 **[2차]**. LINE은 수백만 행 규모의 앱에서 CLAUDE.md를 약 150행으로 줄였다 ([Speaker Deck](https://speakerdeck.com/lycorptech_jp/20260218e)). 결정 기록에는 외부 작업 메모리를 쓴다. 컬리는 compact 전에 결정사항을 `docs/decisions.md`에 남긴다 ([컬리 기술블로그](https://helloworld.kurly.com/blog/vibe-coding-with-claude-code/)).

## 표준 스택은 AGENTS.md·Agent Skills·MCP이고, hooks는 사실상의 표준에 머문다

AAIF는 2025-12-09 Linux Foundation의 directed fund로 출범했다. 창립 프로젝트는 Anthropic의 MCP, Block의 goose, OpenAI의 AGENTS.md이고, Platinum 회원은 AWS, Anthropic, Block, Bloomberg, Cloudflare, Google, Microsoft, OpenAI다 ([LF press release](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation); [Anthropic 공지](https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation)). Google이 2025-04 발표한 A2A는 2026-08-17 AAIF 호스티드 프로젝트가 됐다 ([AAIF Blog](https://aaif.io/blog/a2a-joins-aaif)). MCP 기증일을 2026-05로 적은 2차 출처가 있지만 1차 자료와 맞지 않아 오류로 판단했다.

| 표준 | 역할 | 거버넌스 | 2026-11 상태 |
|---|---|---|---|
| AGENTS.md | 저장소 지시 ("README for agents") | AAIF/LF | 스키마·버전 없음, 가장 가까운 파일이 우선 |
| Agent Skills (SKILL.md) | 절차 지식 패키지 | agentskills.io 오픈 스펙 (AAIF 이관 여부 미확인) | `.agents/skills/`가 교차 클라이언트 관례 |
| MCP | 에이전트 ↔ 도구 | AAIF/LF, SEP 프로세스 | 2026-07-28 개정 (stateless, breaking) |
| A2A | 에이전트 ↔ 에이전트 | AAIF/LF | v1.0 안정판 (2026-03~04) |
| Hooks | 라이프사이클 이벤트 | **표준 없음** | Claude Code 모델이 사실상 표준 |
| ACP / AG-UI / OTel GenAI | 에디터↔에이전트 / 에이전트↔UI / 트레이싱 | Zed·JetBrains / CopilotKit 주도 / OTel | OTel agent span은 Development 상태 |

**AGENTS.md**는 필수 필드가 없는 자유 형식 Markdown이다. 중첩 시 가장 가까운 파일이 우선하고, 사용자 프롬프트가 모든 것을 덮어쓴다. Codex, Jules, Cursor, Copilot coding agent, Gemini CLI, Zed, Devin, Junie 등이 채택 목록에 올라 있다 ([agents.md](https://agents.md)). Codex는 git 루트에서 cwd까지 내려가며 디렉터리마다 최대 한 파일을 이어 붙이고, 합계 **32 KiB**(`project_doc_max_bytes`)에서 멈춘다 ([Codex docs: AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)). 가장 큰 변화는 Claude Code다. **v2.1.277부터 내장 플러그인으로 AGENTS.md를 직접 읽는다.** 다만 기본 모드(`claude-md-or-agents-md`)에서는 cwd나 그 상위에 CLAUDE.md가 **없을 때만** 로드한다. CLAUDE.md가 따로 필요하다면 그 안에 `@AGENTS.md` import를 넣어야 하고, Codex 전용인 `AGENTS.override.md`는 Claude Code가 읽지 않는다 ([Claude Code docs: memory](https://code.claude.com/docs/en/memory)). 이 버전이 2026-09-18에 나왔다는 날짜는 2차 보도로만 확인했다 **[2차]** ([Hacker News](https://news.ycombinator.com/item?id=49760187)). Copilot은 AGENTS.md와 함께 루트의 CLAUDE.md, GEMINI.md도 읽는다 ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)). Gemini CLI는 설정에서 context 파일명을 AGENTS.md로 지정해야 한다 ([agents.md](https://agents.md)).

**Agent Skills**는 Anthropic이 2025-10-16 공개하고 2025-12-18 오픈 표준으로 전환했다 ([Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)). 형식은 `SKILL.md`(필수 frontmatter `name` 1~64자이고 디렉터리명과 같아야 함, `description` 1~1024자)와 선택적인 `scripts/`, `references/`, `assets/`로 구성된다. 로딩은 3단계 progressive disclosure다. 카탈로그는 스킬당 약 50~100토큰, 본문은 5,000토큰 미만 권장, 리소스는 필요할 때 로드한다 ([agentskills.io spec](https://agentskills.io/specification); [client guide](https://agentskills.io/client-implementation/adding-skills-support)). 경로는 클라이언트마다 다르다. Codex는 `.agents/skills` ([Codex docs: skills](https://learn.chatgpt.com/docs/build-skills)), Gemini CLI는 `.agents/skills`를 `.gemini/skills`보다 우선 ([Gemini CLI skills](https://geminicli.com/docs/cli/skills/)), Copilot은 `.github/skills`, `.claude/skills`, `.agents/skills`를 모두 읽는다 ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/about-agent-skills)). Claude Code 문서는 `.claude/skills/`만 명시하고, `disable-model-invocation`, `context: fork` 같은 확장 필드를 더한다. 확장 필드는 claude.ai 업로드나 Skills API에서는 하드 에러를 낸다 ([Claude Code docs: skills](https://code.claude.com/docs/en/skills)).

**MCP**의 현행 개정은 **2026-07-28**이고, 큰 breaking change다. `initialize` 핸드셰이크와 세션(`Mcp-Session-Id`)이 제거됐고, 요청마다 `_meta`로 버전과 capability를 협상한다. `server/discover`가 필수가 됐고, Tasks는 확장으로 분리됐다. OpenTelemetry trace context 전파가 명문화됐다. Roots, Sampling, Logging, HTTP+SSE 전송, OAuth Dynamic Client Registration은 **[폐기]** 상태이며, 최소 12개월의 deprecation 기간을 정한 정책이 생겼다 ([MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). 공식 registry는 여전히 preview다 ([MCP registry](https://modelcontextprotocol.io/registry/about.md)). Codex는 MCP 도구를 자체 샌드박스 밖에서 실행하므로 MCP 서버가 직접 가드레일을 걸어야 한다 **[2차]** ([InfoQ](https://www.infoq.com/news/2026/02/codex-agent-loop)). 도구 간에 공유하는 MCP 설정 파일 표준은 없다.

**Hooks**에는 공식 표준이 없지만 계약은 수렴했다. 핸들러가 stdin으로 JSON을 받고, exit 2면 차단하며 stderr가 이유가 된다. 이벤트 이름은 PreToolUse/PostToolUse 계열이다. Claude Code에는 33개 이벤트와 `command`/`http`/`mcp_tool`/`prompt`/`agent` 핸들러가 있다 ([Claude Code hooks](https://code.claude.com/docs/en/hooks)). Codex는 Claude식 PascalCase 이벤트를 쓰고 `CLAUDE_PLUGIN_ROOT`를 호환용으로 주입한다 ([Codex hooks](https://learn.chatgpt.com/docs/hooks)). Gemini CLI는 BeforeTool/AfterTool처럼 이름은 다르지만 exit 2 계약은 같다 ([Gemini CLI hooks](https://geminicli.com/docs/hooks/)). Cursor는 camelCase 이벤트를 쓰면서 Claude Code hook을 그대로 로드할 수 있다 ([Cursor hooks](https://cursor.com/docs/agent/hooks)). 공통 교집합은 SessionStart/End, 프롬프트 제출, 도구 전후, pre-compact, stop이다.

주변 프로토콜 가운데 하네스와 직접 관련 있는 것은 셋이다. **ACP**(Agent Client Protocol)는 LSP를 본뜬 stdio JSON-RPC로 에디터와 코딩 에이전트를 잇는다. 2026-01 Zed와 JetBrains에 ACP Registry가 생겼다 ([agentclientprotocol.com](https://agentclientprotocol.com/overview/introduction); [Zed blog](https://zed.dev/blog/acp-registry)). **AG-UI**는 에이전트 백엔드에서 프론트엔드로 가는 이벤트 스트림 규약이다 ([AG-UI docs](https://docs.ag-ui.com/introduction)). **OTel GenAI semantic conventions**는 `invoke_agent`, `execute_tool` 스팬과 `gen_ai.usage.*_tokens` 속성을 정의하지만, 에이전트 스팬은 아직 **Development** 상태이고 태그된 릴리스가 없다 ([OTel agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)).

## 국내 실무는 "구조로 강제하라"와 "하네스를 줄여라"를 동시에 말한다

국내에서 공개된 자료 가운데 가장 실무적인 것은 카카오페이 「AI Agent, 넌 누구냐」 연작이다. 1편(2026-09-01)은 하네스의 역할을 제어, 감시, 개선으로 정의한다. 루프 종료 기준 세 가지(모델의 완료 선언, 반복·토큰 예산, 외부 검증) 가운데 **외부 검증이 가장 신뢰할 만하다**고 정리한다 ([카카오페이 1편](https://tech.kakaopay.com/post/ai-agent-1/)). 2편(2026-11-03)은 hook 7개를 4개 이벤트에 배치한 설계를 공개했다. `UserPromptSubmit`은 스킬 라우팅, `PreToolUse`는 선행 산출물이 없는 단계 차단, `PostToolUse`는 lint와 타입체크 결과 기록 및 실패 시 되돌림, `Stop`은 필수 단계가 남았으면 종료 차단을 맡는다. 검증 결과는 에이전트의 주장이 아니라 실제 명령 실행 결과로 기록한다. 같은 글은 모델이 좋아지면서 2026년 2월부터 10월 사이에 **에이전트 21개 → 11개, 스킬 29개 → 17개**로 하네스를 줄였다고 밝힌다. 남은 것은 코드에서 추론할 수 없는 팀 컨벤션과 검증·릴리스 게이트다. 사라진 것은 단계 쪼개기, 강압적 프롬프트, 페르소나 라우팅이다. 미해결 과제로는 **"지표가 없으면 하네스는 커지기만 한다"**를 꼽았다 ([카카오페이 2편](https://tech.kakaopay.com/post/ai-agent-2/)). Anthropic의 메타원칙과 정확히 겹친다. 하네스의 모든 구성요소는 "모델이 혼자 못하는 것에 대한 가정"이고, 모델이 바뀌면 하나씩 제거하며 무엇이 실제로 하중을 받는지 확인해야 한다는 것이다 ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)).

다른 기업들도 같은 방향을 보인다. 토스는 Claude Code를 "Claude 모델을 위한 Harness"로 보고 소프트웨어 아키텍처에 대응시켰다. Slash Command는 Controller, Skill은 도메인 컴포넌트, MCP는 Adapter, CLAUDE.md는 package.json이다. 결정적 로직은 스크립트로, HITL은 비가역·고위험 결정에만 두라고 한다 ([toss.tech](https://toss.tech/article/44539)). 오픈소스 `toss/apps-in-toss-harness`는 Claude Code 플러그인으로 배포되면서 Codex와 Cursor도 지원한다. MCP와 `llms.txt`를 폴백으로 두고, 심사 제출 같은 비가역 작업은 사용자 승인 후에만 실행한다 ([GitHub](https://github.com/toss/apps-in-toss-harness)). 우아한형제들은 Cursor rules와 skills 앞에 전처리 스크립트를 두어 코드베이스에서 메타데이터만 JSON으로 추출했다. 그 결과 전달 데이터가 평균 약 96.5% 줄고 도구 호출이 4회에서 1회로 줄었는데, 품질 지표는 체감 수준이라고 밝혔다 ([우아한형제들](https://techblog.woowahan.com/26177/)). 컬리는 Plan → Act → Verify 루프, 디렉터리별 CLAUDE.md, PR 전 다중 페르소나 리뷰를 쓴다. 15턴에 걸쳐 Zustand 지시가 Redux 패턴으로 되돌아간 "학습데이터 편향" 실패도 기록했다 ([컬리](https://helloworld.kurly.com/blog/vibe-coding-with-claude-code/)). LY/LINE은 서비스 저장소에는 얇은 caller 워크플로만 두고, 중앙 DevOps 저장소가 프롬프트, 정책, 권한을 소유하는 AI 코드리뷰 플랫폼을 만들었다. GitHub App의 PR 스코프 단기 토큰과 사내 프록시 경유 Bedrock을 쓰며, 약 1개월 동안 32개 저장소에서 344회 리뷰를 했다 ([LY 테크블로그](https://techblog.lycorp.co.jp/ko/building-ai-code-review-platform-with-claude-code-action)). 카카오페이의 spec-kit 실전기는 constitution → specify/clarify → plan → tasks → analyze → implement 순서를 따르되, 문제가 생기면 코드를 고치지 않고 spec으로 돌아가 하위 산출물을 재생성한다 ([카카오페이 SDD](https://tech.kakaopay.com/post/ifkakao-agentic-coding/)). 네이버 D2의 NaverMadCat 멀티에이전트 프레임워크(2026-06-30)는 애그리게이터 요약으로만 확인했다 **[2차]** ([pile 요약](https://piletech.kr/articles/111697)).

용어도 정리해 둘 필요가 있다. 국내 커뮤니티는 프롬프트 → 컨텍스트 → 하네스 → 루프 엔지니어링의 계층으로 설명하는 경우가 많다. SK AX(2026-08-28)는 하네스를 "작업장", 루프를 "작업장의 운영 방식"으로 비유한다. 루프 구성요소로는 트리거·스케줄, worktree, builder/verifier 분리, 대화 밖의 상태 파일을 든다 ([SK AX](https://www.skax.co.kr/insight/trend/3840)). 다만 "루프 엔지니어링"의 기원(Addy Osmani, 2026-06)은 SK AX의 언급으로만 확인했다 **[2차]**. 이 용어는 기업 실무 글보다 컨설팅·미디어·커뮤니티에서 주로 쓰인다. 업계 1차 자료의 표준 용어는 여전히 **harness engineering, context engineering, agentic loop**다. 한 개인 블로그는 "오래된 패턴(ReAct)에 붙은 새 이름"이라고 비판하기도 했다 **[개인]** ([BirdSpring](https://birdspring.com/loop-engineering-facts-2026)). 한국 기업 가운데 정량 eval(성공률, 오탐률, 비용)을 공개한 곳은 사실상 없다.

## 결론

이번 조사에서 가장 중요한 발견은 업계가 "더 똑똑한 루프"가 아니라 **"더 얇은 루프와 더 단단한 경계"**로 수렴하고 있다는 점이다. 모델이 좋아질수록 단계 분해, 페르소나 라우팅, 강압적 프롬프트, context reset 같은 *모델 보정용* 장치는 사라진다. 끝까지 남는 것은 결정적 검증 게이트, 권한·샌드박스 경계, 외부 상태 저장, 사람의 최종 승인 같은 *강제 장치*다. Anthropic, 카카오페이, OpenAI 사례가 각자 독립적으로 이 결론에 도달했다. 그래서 하네스 설계의 진짜 과제는 구성요소를 더하는 일이 아니라 **각 구성요소가 어떤 모델 한계를 가정하는지 기록하고 측정 가능하게 제거하는 일**이다. 업계가 아직 풀지 못한 질문, 곧 하네스 커버리지와 품질을 어떻게 재는가는 신규 도구가 차별화할 수 있는 지점이다.

표준화 측면에서는 "지시(AGENTS.md)와 도구(MCP)는 공식 표준, 절차(Skills)는 오픈 스펙, 이벤트(hooks)는 사실상의 표준, 관측(OTel GenAI)은 아직 개발 중"이라는 비대칭이 남아 있다. 따라서 도구 비종속 하네스는 앞의 두 층은 표준 파일을 그대로 쓰고, 뒤의 두 층은 자체 정규화 계층을 두되 언제든 교체할 수 있게 설계하는 것이 현실적이다. MCP 2026-07-28처럼 표준 자체가 breaking 개정을 하는 시기이므로, 특정 버전에 직접 결합하지 말고 어댑터로 격리해야 한다.

### 저장소 레이아웃: AGENTS.md를 원본으로, 도구별 파일은 얇은 shim으로

공식 멀티툴 템플릿은 없다. 아래는 문서화된 관례(AGENTS.md 원본, `.agents/skills/` 교차 디렉터리, Claude식 hook 계약)를 조합한 안이다. 핵심 규칙은 다섯 가지다. 첫째, **CLAUDE.md는 만들지 않거나, 만든다면 `@AGENTS.md` import 한 줄을 넣는다.** CLAUDE.md가 있으면 Claude Code 기본 모드가 AGENTS.md를 무시한다. 둘째, Codex의 32 KiB 상한을 고려해 AGENTS.md 체인 전체를 작게 유지하고, 루트는 100~150줄짜리 "지도"로 둔다. 셋째, `AGENTS.override.md`는 쓰지 않는다. 넷째, 스킬 frontmatter는 스펙 필드(`name`, `description`, `license`, `compatibility`, `metadata`)만 쓴다. 다섯째, MCP와 hook 설정은 하나의 매니페스트에서 Go 생성기로 도구별 파일을 만든다. 도구 간 공유 설정 표준이 없기 때문이다. Windows 사용자가 있다면 symlink 대신 import 방식을 우선한다. (근거: 표준 스택 장)

```
AGENTS.md                         # 원본 지도 (~100-150줄), 검증 명령을 첫머리에
backend/AGENTS.md                 # Go 전용 (nearest-wins)
frontend/AGENTS.md                # Next.js 전용
CLAUDE.md                         # 선택: "@AGENTS.md" + Claude 전용 메모만
.agents/skills/<name>/SKILL.md    # 원본 스킬 (Codex/Gemini/Copilot 네이티브)
.claude/skills -> ../.agents/skills
.claude/settings.json  .codex/hooks.json  .gemini/settings.json  .cursor/hooks.json
                                  # 모두 생성물: harness.yaml → scripts/hooks/* 등록
.mcp.json (+ 도구별 MCP 설정 생성물)
harness.yaml                      # 단일 매니페스트: gates, hooks, mcp, budgets
scripts/hooks/                    # 단일 구현, 이벤트명 정규화 (PascalCase/camelCase)
docs/specs/  docs/plans/active|completed/  docs/decisions.md
.loop/features.json  .loop/progress.md   # 에이전트는 passes 필드만 수정
```

### 검증 게이트: exit code가 유일한 진실

게이트는 세 층으로 둔다. (1) **computational 게이트(필수)**: `go build`, `go vet`, `go test ./...`, `tsc --noEmit`, eslint, `next build`. (2) **E2E/시각 게이트(선택)**: Playwright. (3) **inferential 게이트(선택, 비용 대비 효과가 확인될 때)**: 대화를 보지 않은 fresh 컨텍스트의 읽기 전용 리뷰어 에이전트를 둔다. 게이트 실행은 반드시 하네스가 직접 하고, 에이전트가 보고한 결과는 기록하지 않는다. 카카오페이 실패 사례를 막으려면 다음이 필요하다. `set -o pipefail`을 강제하고, 에이전트가 게이트 명령에 파이프를 붙이지 못하게 하고, `git stash`·`reset --hard`처럼 공유 워킹트리를 파괴하는 명령을 hook으로 차단하고, 세션마다 worktree를 격리한다. 게이트 실패 출력은 정제해서 다음 반복의 입력으로 넣는다. 커스텀 linter 메시지에는 "고치는 방법"을 함께 적는다. 각 반복을 시작할 때 Anthropic의 세션 시작 루틴처럼 smoke 게이트를 먼저 돌려 이미 깨진 상태를 분리한다. (근거: 검증 게이트 장, 국내 실무 장)

### 루프 제어: 코드가 소유하는 결정적 컨트롤러

Go 백엔드의 루프는 ADK·Agents SDK·Stripe Blueprints처럼 **결정적 노드와 에이전트 노드를 섞은 그래프**로 모델링한다. 종료 엣지는 네 종류다. 게이트 통과, `max_iterations`, 토큰·달러 예산, 에스컬레이션(사람에게 넘김)이다. 기본값은 "반복당 한 항목", "반복마다 새 컨텍스트", "CI성 재시도는 2라운드 후 사람에게"로 둔다. 각 에이전트 CLI는 교체 가능한 executor로 다룬다. Claude Code는 `claude -p`(재현성이 필요하면 `--bare` + 명시적 주입, `--max-turns`, `--max-budget-usd`), Codex는 `codex exec --json --output-schema`(JSONL 이벤트 수집), 그 밖에는 ACP 어댑터를 쓴다. 이렇게 하면 하네스가 Managed Agents가 말하는 "meta-harness"가 된다. CLI 내부의 Stop hook은 보조 장치로만 쓰고, 최종 종료 판정은 바깥 컨트롤러가 내린다. 고위험·비가역 행동(배포, 머지, 외부 전송)은 에이전트에게 권한을 주지 않는다. 사람 승인 노드를 두거나 PR까지만 허용한다. (근거: 루프 수렴 장)

### 상태와 관측성: append-only 이벤트 로그와 OTel 모양의 스팬

도메인 모델은 `Run`(목표, 스펙 참조, 예산), `Iteration`, `Event`(append-only), `Gate`/`GateResult`(명령, exit code, 출력 요약), `Artifact`(핸들 참조), `Checkpoint`(git SHA)로 구성한다. 하네스는 stateless로 두고 이벤트 로그에서 재개한다. compaction이나 요약은 원본을 보존한 위에서만 한다. 텔레메트리 필드는 OTel GenAI 어휘에 맞춘다. 반복은 `invoke_agent`, 도구 호출과 게이트는 `execute_tool`, 그리고 `gen_ai.usage.input_tokens/output_tokens`와 `error.type`을 기록한다. 이 어휘는 Development 상태이므로 semconv 버전을 고정한다. 모든 CLI의 hook을 정규화해 백엔드로 보내면 그대로 텔레메트리 수집점이 된다. Next.js 대시보드로는 SSE로 스트리밍하면 충분하다. 생태계 연동이 필요해지면 AG-UI 이벤트 스키마를 검토한다. (근거: 상태 장, 표준 스택 장)

### 평가와 하네스 다이어트: 지표 없이는 하네스가 커지기만 한다

실행 기록을 처음부터 Anthropic의 eval 스키마(task, trial, grader, transcript, outcome)로 저장하면, 같은 데이터로 하네스 자체의 eval이 가능해진다. 자기 저장소의 실제 실패 20~50개로 작은 regression 세트를 만들고, **pass^k, 반복 수, 토큰과 달러, 사람 개입 횟수, 재작업률**을 추적한다. 하네스 구성요소(스킬, hook, 게이트, 프롬프트 조각)마다 "어떤 모델 한계를 가정하는가"라는 메타데이터를 달고, 모델을 업그레이드할 때 하나씩 꺼 보는 **ablation 실행**을 일급 기능으로 둔다. Anthropic과 카카오페이가 모두 요구했지만 아직 도구화되지 않은 영역이다. 마지막으로 OpenAI 사례의 doc-gardening이나 GC처럼 낡은 문서와 규칙을 찾아 정리 PR을 여는 주기 루프를 내장 템플릿으로 제공하면, "루프 엔지니어링"이라는 이름에 맞는 차별점이 된다. (근거: 검증 게이트 장, 국내 실무 장, 결론)
